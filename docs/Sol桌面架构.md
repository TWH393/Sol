LoadingMark由WPF绘制，每个桌面进程随机一次轻环绕/轻呼吸，沿用透明Logo与动态主题颜色。在页面和真实服务均就绪后撤罩，API健康不等于QQ已连。未启用自动登录时正常入管理；需扫码时复用Sol扫码窗口；8秒提供先入管理，90秒结束等待显示实际阶段，不因此重复登录。不可见/卸载/失败时清理动画clock，遵守Windows动画设置。

网页按当前按钮/表单/页面提供等待，导航、任务和聊天互不锁住。同页面在途相同写请求合并，断网超时不自动重试，结果不确定要求先查记录。状态读取有限超时，后台刷新不覆盖在途表单。桌面与引擎同时发布需完整更新，普通引擎更新仍可保留窗口。上述尚未实际运行验收。

## 消息轮次、收发与后台优先级修订（2026-11-02）

本节覆盖下文早期“新消息调整旧回复”和“单发送队列”的描述。文字与图片/文件分别排队，附件通道一次处理一个上传，独立等待回执，文字通道不等上传。原生QQ统一在真正调用SDK发送前控制配置中的2～3秒间隔，仅串行取得发送机会，不串行等待上传；OneBot代理不对原生接入重复限速。框架兼容接入仍沿用自己的发送控制。只有真实成功回执才归档已发送，记录真实QQ消息编号，失败或中断不自动重发。

连续补充仅在同一机器人、同一会话、同一发言人窗口内合并。每段保留消息编号、发言人、引用来源和附件编号；缺失引用明确标记，不能拿最近消息替代。首条消息快照确定可读上下文边界，本人窗口内补充作为该轮内容更新；其他人或后续新轮次不会让旧判断作废、取消旧回复或自动修改旧任务。历史消息按SQLite记录边界读取，保留来源的完整批次交主模型理解比较/替换/指代；记忆权限与明确任务修改/取消权限仍独立校验。

本地助手对话判断/记忆筛选优先；后台记忆整理、人格复盘与冷场话题判断在空闲时进行。新消息到达取消正在进行的后台HTTP子请求，释放锁后优先前台，后台保留原输入并在空闲后重试，不写入半成品结果。多个前台请求在原超时内等待，而不因后台占用就立即跳过；取消HTTP不保证推理后端在同一瞬间停算。GPU绘图占用时仍保留原暂停/卸载规则。

原生QQ入站引用经同会话缓存/SDK记录确认，出站用ReplyElement引用实际触发本轮的消息，优先选择带明确问题/引用/附件的本方消息。首个发送尝试取得引用，其余气泡保留关联但不重复引用；原引用取不到时短超时后按普通消息发送，不伪造成功引用，后台记录实际quoted状态。QQ引用不是任务授权。对其他人的真实@不作本轮扩展，沿用此前边界。

重启保留记忆、配置、文件和历史，普通执行任务与待发送消息不恢复、不补发。新版set_reminder创建的未来安排保存到future_tasks；QQ在线时由共享调度器继续。后台reminders.catch_up_once/catch_up_recurring分别决定一次性和周期错过的是否补发，默认一次性补发、周期不补发；周期开启后合并错过时点为一次补发。future_runs在提交前记录本次处理，启动时sending转送达未确认，不自动重复发送。旧版已中断的提醒不擅自恢复。启动时待发管理通知仍标为已丢弃（delivered=-1，非已送达），QQ接收忽略本接入启动之前的离线消息。普通引用/会话目标只驻留当前服务内存；未来提醒单独保存创建时实际观测的账号/目标/peer授权，仅匹配同机器人同会话的有效提醒可以使用，不回灌普通发送目标表。手动重发文件依旧需当前服务实际接收过该目标会话消息。

正常桌面和网页使用同一页面：取消旧interrupt开关，说明同人合并、每轮独立及文字/附件分队列。会话页可展开合并消息和引用来源。上述只完成源码和静态构建，未进行QQ、模型、上传、优先级或重启功能验收。

正常入口改为`UnifiedWindow.cs`：C#外壳管理窗口、托盘、单实例、自启动和引擎；WebView2承载完整现有前端，使用相同API、Cookie、配置、密钥库和数据。常规操作不再跳浏览器管理页。下载调用桌面保存对话框；GPT官方授权因浏览器登录隔离仍由系统浏览器本人操作，完成后回Sol管理。WebView2的页面目录位于state/desktop/webview，不纳入分发。

原MainWindow/WPF业务页面只保留旧颜色预览路径，正常应用不创建；不继续开发两套业务界面。第6项记忆未改，既有记忆页面原样进入桌面。下面的原生/浏览器分工为历史架构记录，以本节为准。

### 收消息与本地判断重叠（2026-11-02）

启用消息合并时，首条消息到达立即做本地话题/接话/工具分类，与chat.wait_seconds等待重叠，合并计时器仍按原来的等待/最长等待规则运行。消息批次编号、引用、最近消息上下文全部相同才复用结果，避免第二次调用；新补充取消旧判断，最终收齐后判断完整批次一次，不对每条补充重启推理。上下文变化同样不能复用。

预处理仅调用已有本地助手，不触发主模型、附件读取、记忆写入、回复或任务执行。本地模型忙/暂停时跳过提前处理，窗口结束回到正常逻辑。Chat.preparing统一跟踪预处理和正式请求准备阶段，断联/退出会取消，合并开关变化不遗留旧计时器。记忆筛选仍按原规则在正式请求中执行，后台记忆整理继续独立。仅静态构建，未测量实际速度，不保证每轮固定省2秒。

- C# / WPF 负责真正的原生窗口、侧栏、托盘、单实例、Windows 登录自启动，以及内部引擎的启动和退出。
- Python 负责 AstrBot、QQ、模型与工具。在应用内部启动，不再创建 Python 窗口、托盘或自启动项。
- 浏览器管理页保留，和原生窗口使用同一个配置、数据库和 API。
- 内部 `companion` 包名、数据库名和现有数据目录暂不更名，避免只为品牌变化破坏路径或凭据。
- 不使用旧生产环境的登录信息、消息历史或运行服务。

## 原生页面的当前范围

外观默认暖白+陶土橙，保留暗色模式。原生和浏览器顶部都有切换入口，持久选择保存在统一配置`app.theme`，不重启核心或模型。原生`Theme.cs`管理语义调色板，`Themes/Controls.xaml`管理控件；浏览器用`theme.js`缓存首屏、`theme.css`提供浅色覆盖，并以引擎状态中的主题值为准。窗口、输入、表格、Logo和托盘跟随选择；第一张主Logo对应浅色，第二张对应暗色。纯外观变化不建立额外数据库备份。

原生提供总览、会话记录查看、任务记录及取消、文件记录及保存、记忆记录、人格版本记录、模型添加/密钥/切换与思考强度、GPT登录发起、调用记录、功能开关、插件记录、活动记录、基础账号、自启动、QQ授权/扫码状态和气泡数量/间隔设置。2026-11-01按用户要求沿用网页审美：同一语义配色、侧栏图标与分区、面包屑、大标题、圆角卡片、留白及统一顶部按钮。浏览器完整管理页继续保留。

细化额度、模型配置高级编辑、记忆编辑、人格曲线、插件安装和其他高级操作仍使用浏览器完整管理页。当前是第一阶段原生桌面，不能称为所有高级页面都迁移完毕。QQ面板通过共享API获取本应用组件的二维码与状态，不添加第二套接入或配置数据库。

## 所有权与生命周期

1. 原生程序先持有数据目录对应的 Windows 命名互斥对象。同目录重复启动只请求显示已运行的主窗口。旧预览入口也使用相同互斥对象名称。
2. 启动前检查本应用配置的监听端口。端口被占用就给出原因，不连接或杀死占用进程。
3. 新建随机桌面凭据，经子进程环境传递。只监听本机的 HTTP 管理接口同时支持浏览器会话 Cookie 和此桌面凭据。
4. 原生程序验证子进程 PID、数据目录和协议版本，确认连接的是自己启动的引擎。
5. 关闭窗口进入托盘；显式退出才停止引擎。原生进程与引擎之间保留 stdin 管道，父进程退出或崩溃时管道关闭，引擎执行正常停止流程。
6. 正常停止会中断未完成工作并停止本应用管理的服务。等待超过 150 秒才结束自己拥有的进程树，同时明确提示容器停止状态未确认；不声称任意崩溃都能清理外部容器。
7. 网页修改自启动开关后，原生程序的本地状态刷新负责同步注册表。不会启动第二套 Python 自启动项。旧项目自启动项只有路径准确指向本项目旧入口时才移除。

### 本地辅助模型退出回收（2026-11-02）

Windows下，Sol新建的私有Ollama由标准库守护进程启动。守护进程先加入开启KILL_ON_JOB_CLOSE的Windows Job，再创建Ollama；后续llama-server继承Job，避免“父进程已结束、模型仍占显存”。唯一Job句柄不继承给子进程。正常停止关闭引擎到守护进程的stdin；引擎异常退出也关闭管道；守护进程被强制结束则由Windows关闭Job句柄，回收同组模型进程。退出时QQ停止异常不会阻断后续内部服务清理。

仅管理本次由Sol创建的服务；已存在的服务不会被接管或结束，不按进程名批量杀进程。进程组保护建立失败时停止启动并保留具体原因，不降级为无保护启动。state/local-service.json记录本次随机启动标识、守护/服务PID和阶段，启动握手不请求模型推理。关闭窗口收进托盘仍继续运行，完全退出才清理。

这部分仅完成静态构建，尚未由用户验收退出或崩溃回收。

## 构建与私有引擎

- Visual Studio 打开根目录 `Sol.sln`；启动项目 `Sol.Desktop`。构建需要 .NET 10 SDK 与 WPF 开发支持。
- `scripts/build-desktop.ps1 -BundleEngine -IncludeResources -CreateShortcut` 构建本机已准备版本，生成 `build/Sol/Sol.exe` 和桌面 `Sol` 快捷方式。
- .NET 使用 self-contained 发布，发布目录自带运行时。
- 私有 Python 使用完整 CPython 的解释器、标准库与本项目已安装依赖，**不会直接复制一个不能可靠搬家的 .venv**。去掉 editable 引用、绝对路径 `.pth` 与安装来源文件。
- 自有源文件独立复制；不可变依赖与模型文件可使用硬链接节约本机磁盘。源码和用户配置不使用硬链接。
- 引擎、准备好的 Ollama / Whisper 资源和匹配 Playwright 版本的浏览器放入发布目录；不复制整个用户运行目录。
- 当前本机版明确继续使用项目 `state/` 数据。`-FreshUserData` 可让发布配置改用 `%LOCALAPPDATA%/Sol/data`，不复制现有账号和历史。
- 本地绘图环境、Docker Desktop、Git、Node 等外部能力仍有前置依赖；此次没有重新封装这些第三方软件。

## 2026-11-02 加载层可见性与就绪信号

UnifiedWindow使用WebView2CompositionControl替代HWND WebView2，避免浏览器始终盖住WPF加载层。参考[微软WPF WebView2说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/platforms/wpf)。NavigationCompleted只代表导航结束；必须同时等待desktop-startup.js与app.js的实际页面渲染信号，才可因后端ready自动撤罩。boot标记/NavigationId隔离旧页面事件；脚本错误有原生失败界面，不无限显示空白。正常长等待继续动画，扫码等待和实际错误分别说明。只构建，未作新版UI验收。

### CompositionControl的发布依赖

桌面TFM必须为net10.0-windows10.0.17763.0，不能退回只有net10.0-windows的目标。具体Windows TFM让SDK带入WinRT projection runtime；微软说明见[Windows TFM与WinRT](https://blogs.windows.com/windowsdeveloper/2020/09/03/calling-windows-apis-in-net5/)。自包含发布需含Microsoft.Windows.SDK.NET.dll、WinRT.Runtime.dll及对应Sol.deps.json记录，AfterPublish有文件缺失检查。仅编译通过不足以证明新控件的运行依赖完整；本次仍由用户做打开/显示验收。
